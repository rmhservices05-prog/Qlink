ID | Failure / shortcut | Why it matters | Required control
H-01 : Golden-image cloning | Firmware/storage image contains key, nonce prefix, device ID or counter state. | Fleet devices may repeat nonce/key pairs or share identity. | Provision unique identity and cryptographic state after imaging; verify uniqueness in production.
H-02 : Shared fleet AES key | Same symmetric key installed across all aircraft for convenience. | Capture or extraction from one platform can affect many. | Per-platform keys or tightly scoped groups; minimise blast radius.
H-03 : Reboot counter reset | Counter starts from zero after boot. | Same-key nonce reuse; GCM/CCM security failure. | Persistent monotonic state or guaranteed fresh epoch/key after reboot.
H-04 : Hot-standby failover | Backup controller uses same key/counter range. | Nonce collision during takeover. | Allocate disjoint sender IDs/counter spaces or derive independent keys.
H-05 : Ground-station failover | Second GCS transmits under same shared key with overlapping sequence. | Nonce collision and replay ambiguity. | Unique GCS sender domain and authorised handover.
H-06 : Snapshot /database restore | Old state restores a lower counter. | Previously used nonces recur. | Keep cryptographic monotonic state outside normal rollback or force new key/epoch.
H-07 : Random nonce shortcut | Integrator replaces counter management with RNG-generated nonces. | Poor boot entropy or clone state creates collisions. | Prefer deterministic uniqueness construction where possible.
H-08 : Short authentication tags | Tag truncated to save bandwidth. | Forgery probability and safe usage limits worsen. | Treat tag length as security parameter; approve centrally.
H-09 : Header left unauthenticated | Header considered 'not secret'. | Context/type/identity may be altered or packet transplanted. | Authenticate security-relevant header fields as AAD.
H-10 : No replay protection | AEAD assumed to prevent replay. | Recorded valid command can be replayed. | Explicit freshness and replay window.
H-11 : Over-simple replay test | Reject every sequence below last seen. | Valid reordered packets rejected; operators may disable security. | Sliding acceptance window.
H-12 : Fail-open after auth errors | Availability workaround accepts packets after repeated failures. | Attacker deliberately forces auth-failure state. | Authentication failure must never authorise unauthenticated command processing.
H-13 : Maintenance mode bypass | Service mode disables encryption/authentication. | Hidden operational bypass. | Same trust requirements, or physical/isolation controls and explicit audit.
H-14 : Development key retained | Test key survives into production. | Known/common secret compromises fleet. | Production build must reject known test credentials.
H-15 : Keys in logs | Debug output prints keys/state/plaintext. | Maintenance/log infrastructure becomes secret repository. | Prohibit key logging and sensitive state dumps.
H-16 : Keys in crash dumps | RAM secrets copied into support artefacts. | Keys leak via ticketing/cloud/support channels. | Sanitise dumps or protect/segregate them.
H-17 : Long-lived static key | Same key remains indefinitely. | Compromise has large retrospective/future window. | Defined cryptoperiod and rotation/rekey policy.
H-18 : Key reuse across functions | One secret used for encryption, MAC, hopping, recovery, etc. | Cross-protocol compromise and correlated failure. | Domain-separated keys.
H-19 : Hop reset rewinds crypto | Hop index doubles as AES counter. | Resync/reset reuses key/nonce state. | Independent state machines.
H-20 : Jam-to-fallback | Interference automatically switches to AES/weak mode. | Adversary induces downgrade. | Fallback requires authenticated policy/state, not mere link degradation.
H-21 : AES-to-plaintext emergency | Emergency availability bypass disables authentication. | Jamming can induce unauthenticated command channel. | If such a mode exists, treat as separate explicitly authorised security state.
H-22 : Fleet emergency key | Universal recovery secret on every platform. | Single extraction compromises fleet. | Scope by platform/fleet/customer; make revocable and time/epoch limited.
H-23 : Same key both directions | GS and UAV share key and both counters start similarly. | Nonce collisions across directions. | Independent directional keys/domains.
H-24 : Two authorised GCS | Both can transmit with same key/counter space. | Nonce collision and ambiguous command authority. | Unique sender identities and domains.
H-25 : Allied-force key export | Key copied via USB/email/laptop for interoperability. | Key handling becomes weakest link. | Controlled provisioning, audit and scoped credentials.
H-26 : Old key kept forever | Receiver 'tries current then previous' without expiry. | Retired credentials remain usable. | Explicit key IDs, activation and retirement epochs.
H-27 : Execute before verify | Command parsed/acted upon before AEAD verification completes. | Unauthenticated data influences flight. | Verify complete packet before command interpretation/execution.
H-28 : Partial packet processing | Streaming/latency optimisation consumes data before authentication. | Forgery can influence state before failure known. | No command use before authentication success.
H-29 : CRC mistaken for security | RF CRC/checksum treated as proof of authenticity. | Attacker-generated frames pass integrity checks intended only for noise. | Keep accidental-error detection separate from cryptographic authentication.
H-30 : CTR/CBC without MAC | Encryption equated with security. | Malleability/injection remains possible. | Require AEAD or robust encrypt-then-authenticate design.
H-31 : Counter wrap | Small sequence field eventually overflows. | Nonce reuse if key persists. | Calculate lifetime; rotate key/epoch before wrap.
H-32 : Mission reset resets crypto | Application 'new mission' clears packet counters. | Nonce reuse across missions. | Cryptographic lifecycle independent of mission lifecycle.
H-33 : Firmware downgrade | Old signed firmware remains installable. | Patched nonce/auth flaws can be reintroduced. | Anti-rollback policy for security-critical firmware.
H-34 : Factory reset restores insecure state | Reset re-enables defaults, common keys or counter zero. | Security posture silently collapses. | Define secure-reset semantics; test them explicitly.
H-35 : Captured aircraft | Opponent gains physical possession. | Local secrets and fleet-common material exposed. | Minimise cross-platform trust; support rapid revocation/epoch change.
H-36 : FHSS treated as encryption | Hopping assumed to hide content/commands. | Weak key/auth decisions justified by RF obscurity. | Treat hopping as independent availability/collection-resistance layer.
H-37 : Hopping pattern reused across missions | RF pattern changes mistaken for key rotation. | Cryptographic exposure persists. | RF and crypto epochs managed independently.
H-38 : Wideband collection ignored | Assumption that hopping prevents interception. | Traffic may still be collectable by capable receivers. | Maintain strong cryptographic protection regardless of bearer.
H-39 : Exhaustive AES key  searc | Attacker tests candidate AES keys directly against known or recognisable plaintext/ciphertext. | Mode-independent baseline attack. Cost is governed primarily by AES key length; it is not a weakness in a particular mode. | Use an approved key length appropriate to the security lifetime; avoid low-entropy or human-derived AES keys and enforce strong key generation.
H-40 : Biclique cryptanalysis of full AES | Biclique cryptanalysis applies directly to the full-round AES primitive and reduces the work factor slightly below exhaustive search. | Published complexities are about 2^126.1 for AES-128, 2^189.7 for AES-192 and 2^254.4 for AES-256. This is academically significant but not a practical break. | Do not treat AES as having exactly its nominal key-bit margin. For long-lived high-assurance use, retain conservative security margin or avoid dependence on AES.
H-41 : AES-192/256 related-key cryptanalysis | Attacker obtains encryptions under keys having controlled mathematical relationships, exploiting properties of the AES key schedule. | Full AES-192 and AES-256 have published related-key attacks substantially below exhaustive search, but they require a non-standard related-key attack model and are not ordinary single-key attacks. | Never expose attacker-controlled related keys; derive independent keys with domain-separated KDFs. Architectures not using AES are unaffected by this AES key-schedule attack.
